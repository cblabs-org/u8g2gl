# U8G2GL — Critical Concept Evaluation

**A declarative XML-based UI framework for U8G2 monochrome displays, inspired by LVGL Pro.**

---

## The Idea in Brief

Take the architectural ideas from LVGL Pro (XML screen definitions → code generation → reactive data binding) and create a simplified version for U8G2 monochrome displays. The system would include:

1. XML files for screen definitions and designs
2. A binding/subject system for controller↔screen interaction
3. A web-based visual editor
4. Composite widget support (e.g. weather widget)
5. CLI/scripts to compile XML → C code
6. Font management (BDF editor + compiler)
7. Mono asset management (XBM/bitmap pipeline)

**3. A Widget Base Class Hierarchy**
[iGfxWidget](file:///Users/mcneillm/Documents/Projects/departures-board/modules/displayManager/widgets/iGfxWidget.hpp) provides `tick()` / `render()` / `renderAnimationUpdate()` lifecycle — the exact three-phase pattern that U8G2GL should adopt.

**4. Real Composite Widgets**

- [clockWidget](file:///Users/mcneillm/Documents/Projects/departures-board/modules/displayManager/widgets/clockWidget.hpp) — configurable format, blinking colon, dual fonts

**5. `@designer_prop` Annotations**
Several widgets already embed metadata hints for a future visual editor:
```cpp

/// @designer_prop int align = 0 - Horizontal text alignment.
/// @designer_prop bool isTruncated = false - Append ellipsis if text exceeds widget width.
```

**6. Board/Screen Architecture**
[iDisplayBoard](file:///Users/mcneillm/Documents/Projects/departures-board/modules/displayManager/boards/interfaces/iDisplayBoard.hpp) provides the screen lifecycle (`onActivate`/`onDeactivate`/`tick`/`render`) and the layout interface composes widgets into screens.

### What This Means for U8G2GL

The departures-board is the **proof of concept**. U8G2GL is the **generalisation**. The key evolution is:

| departures-board (current) | U8G2GL (proposed) |
|---|---|
| JSON layout format | XML format (richer, more human-readable, component-aware) |
| Hardcoded widget types in schema enum | Extensible widget registry (built-in + custom) |
| Widget properties set imperatively in generated C++ | Declarative property binding via subjects |
| `@designer_prop` annotations (unused) | First-class property metadata driving the visual editor |
| Board-specific layouts only | Generic screens usable by any project |
| No web preview | Browser-based canvas preview |
| Project-specific code generator | Standalone CLI tool |

## Critical Evaluation

### ✅ What's Strong About This Idea

**1. There's a genuine gap in the market.**
Nobody has built a declarative XML → code generation pipeline specifically for U8G2/monochrome displays. Lopaka is the closest, but it's purely a visual layout tool with no binding system, no component model, and no CI/CD-friendly CLI pipeline. The space is ripe.

**2. LVGL Pro provides a proven architectural template.**
You don't need to invent the paradigm. LVGL Pro's separation of `project.xml` / `globals.xml` / `screens/*.xml` / `components/` / `widgets/` is battle-tested and translates well to a simpler domain.

**3. The monochrome constraint is an advantage.**
U8G2 deals with a dramatically simpler rendering model than LVGL:
- 1-bit color (or 2-bit grayscale on some e-paper)
- No anti-aliasing, no gradients, no alpha blending
- Small resolutions (128×64, 128×32, 256×128, etc.)
- Limited primitives: text, lines, boxes, circles, XBM bitmaps

This means the XML schema, code generator, and web preview can all be **much simpler** than LVGL Pro. The entire Wasm preview can run a software framebuffer at negligible cost.

**4. Composite widgets solve a real pain point.**
A "weather widget" that combines an icon + temperature label + description — currently this means manual pixel math every time. Declaring it once and reusing it via `<weather_widget temp="$subject_temp" icon="sunny" />` would be transformative for hobbyists.

**5. The web editor has low technical risk.**
Rendering a monochrome pixel grid in a `<canvas>` is trivial. You don't need Wasm compilation of the actual U8G2 library — you just need a JavaScript renderer that understands the same primitives (draw_str, draw_box, draw_xbm, etc.) and can parse your XML format.

---

### ⚠️ Concerns & Design Tensions

**1. How much "LVGL Pro" is too much?**
LVGL Pro's architecture serves displays with 100+ widgets, touch interaction, animations, and complex state machines. U8G2 screens typically have 5-15 elements and are navigated with buttons/encoders. There's a real risk of **over-engineering** the XML schema and binding system.

> [!IMPORTANT]
> **Recommendation:** Start with a minimal schema. A screen should be 10-20 lines of XML, not 100. Resist the urge to replicate LVGL Pro's full feature set. The value proposition is *simplicity*.

**2. Data binding complexity vs. U8G2 reality.**
LVGL Pro's subject system (`bind_value`, `bind_flag_if_lt`, `bind_state_if_eq`, `bind_style`) is sophisticated because LVGL widgets have rich state (checked, disabled, focused, pressed, etc.). U8G2 has no concept of widget state — it's a framebuffer drawing library. Every frame redraws everything.

This means:
- Bindings can be much simpler — essentially template interpolation (`$variable` → value at render time)
- But you need to define a **render loop model**: when does a screen redraw? On subject change? On a timer? Both?
- Conditional visibility (`<show_if subject="battery" lt="20">`) makes sense, but conditional styling is less useful when you only have black/white

> [!TIP]
> Consider a simple model: subjects are typed variables (`int`, `string`, `bool`). Widgets reference them via `$subject_name`. The screen redraws when any bound subject changes. That's it for v1.

**3. The web editor is the largest engineering effort.**
The XML schema, code generator, and CLI are all tractable weekend-to-week projects. A proper web editor with drag-and-drop, property panels, live preview, undo/redo, and font rendering is a **multi-month effort** even for monochrome. Consider:
- Start with the CLI pipeline first (XML → C code)
- Use a text editor + live preview initially (hot-reload XML in browser)
- Build the full visual editor as a later phase

**4. Runtime XML parsing is not an option.**
Academic literature on declarative UI for resource-constrained systems ([CGui toolchain](https://dl.acm.org/), [UIML mappings](https://ceur-ws.org/)) consistently concludes that MCUs running U8G2 (often 8-bit AVR with 2KB RAM, or ESP32 with limited headroom) **cannot afford runtime XML DOM parsers**. The XML must be compiled to static C data structures or direct API calls at build time — which is exactly what LVGL Pro's AOT pipeline does.

> [!IMPORTANT]
> **This is non-negotiable for the architecture.** XML is a *development-time* format. The CLI compiles it to C. No XML parser ships on the MCU.

**5. Consider borrowing Flipper Zero's navigation model.**
Flipper Zero has the most mature monochrome 128×64 UI architecture in production: `Canvas` → `Viewport` → `View` → `ViewDispatcher` → `SceneManager`. For U8G2GL, a simplified version of this stack (`Screen` → `View` → scene transitions) would give users structured navigation without reinventing it.

**6. Font management scope creep.**
U8G2 already has an excellent font system with 600+ pre-compiled fonts and `bdfconv` for custom fonts. Building a BDF editor is a substantial standalone project. Consider:
- **v1**: Integrate with existing tools (bdfconv, FontForge export). Provide a `<font>` declaration in XML that references BDF files and compiles them via the existing `bdfconv` tool.
- **Later**: Build a simple web-based BDF pixel editor if there's demand.

**7. Competition with Lopaka.**
Lopaka is actively developed, has community traction, and supports multiple platforms. However, its architecture is fundamentally different — it's a drawing tool, not a framework. U8G2GL would be **complementary**, not competitive. You could even export Lopaka designs into your XML format.

---

### 🔴 Risks

**1. Adoption barrier.**
The embedded hobby community is split between "just give me Arduino code" and "I'll write my own framework." A new XML-based workflow is a paradigm shift that requires documentation, tutorials, and example projects to gain traction.

**2. U8G2 API surface is large and quirky.**
U8G2 has multiple drawing modes (`sendBuffer` vs `nextPage`), different controller constructors, and platform-specific initialization. The code generator needs to handle these variations or risk generating code that doesn't compile on specific setups.

**3. Maintenance burden.**
U8G2 is maintained by a single developer (olikraus). If U8G2 API changes, or if the library goes unmaintained, your framework inherits that risk. Consider also supporting Adafruit GFX as an alternative backend.

## Proposed Architecture (Simplified from LVGL Pro)

```
U8G2GL Project Structure:
├── project.xml              # Display type, resolution, U8G2 constructor
├── globals.xml              # Subjects (reactive variables), constants, fonts, assets
├── screens/
│   ├── home.xml             # Screen definitions
│   └── settings.xml
├── components/              # Reusable composite widgets (pure XML)
│   └── weather_widget/
│       └── weather_widget.xml
├── widgets/                 # Custom C-backed widgets (XML + C)
│   └── gauge/
│       ├── gauge.xml
│       └── gauge.c
├── fonts/                   # BDF font sources
│   └── custom_8px.bdf
└── assets/                  # XBM/bitmap mono images
    └── icons/
        ├── wifi.xbm
        └── battery.xbm
```

### Pipeline

```
┌─────────────────────────────┐
│  XML Screen Definitions     │
│  + globals.xml subjects     │
│  + components/*.xml         │
└──────────┬──────────────────┘
           │
           ▼
┌─────────────────────────────┐
│  u8g2gl CLI                 │
│  • validate                 │
│  • generate (XML → C)       │
│  • preview (launch browser) │
│  • font-compile (BDF → C)   │
│  • asset-compile (XBM → C)  │
└──────────┬──────────────────┘
           │
           ▼
┌─────────────────────────────┐
│  Generated C Code           │
│  • ui_screens.h / .c        │
│  • ui_subjects.h / .c       │
│  • ui_fonts.h / .c          │
│  • ui_assets.h / .c         │
│  DO NOT EDIT (regenerated)  │
└─────────────────────────────┘
```

### Example XML

```xml
<!-- project.xml -->
<project name="weather-station" version="1.0">
  <display controller="SSD1306" width="128" height="64" bus="i2c" />
</project>
```

```xml
<!-- globals.xml -->
<globals>
  <subjects>
    <int name="temperature" value="22" />
    <int name="humidity" value="45" />
    <string name="status" value="OK" />
    <bool name="wifi_connected" value="true" />
  </subjects>
  <fonts>
    <font name="main" src="fonts/custom_8px.bdf" size="8" />
  </fonts>
  <assets>
    <xbm name="icon_wifi" src="assets/icons/wifi.xbm" />
    <xbm name="icon_battery" src="assets/icons/battery.xbm" />
  </assets>
</globals>
```

```xml
<!-- screens/home.xml -->
<screen name="home">
  <view layout="vertical" padding="2">
    <!-- Status bar -->
    <row height="10" align="spread">
      <xbm src="icon_wifi" show_if="$wifi_connected" />
      <label text="$status" font="main" />
    </row>

    <!-- Main content -->
    <weather_widget temp="$temperature" humidity="$humidity" />

    <!-- Footer -->
    <label text="Last update: $last_update" font="main" y="56" />
  </view>
</screen>
```

```xml
<!-- components/weather_widget/weather_widget.xml -->
<component name="weather_widget">
  <api>
    <prop name="temp" type="int" />
    <prop name="humidity" type="int" />
  </api>
  <view layout="vertical">
    <label text="$temp°C" font="large" />
    <label text="Humidity: $humidity%" font="main" />
  </view>
</component>
```

## Phased Delivery Recommendation

### Phase 1 — Core Pipeline (MVP)
- [ ] XML schema definition (project, globals, screens, components)
- [ ] CLI tool: `u8g2gl validate` + `u8g2gl generate`
- [ ] Code generator: XML → U8G2 C code (sendBuffer mode)
- [ ] Simple subject system (int/string/bool variables, template interpolation)
- [ ] Asset compilation (XBM → C arrays)
- [ ] Font integration (wrapper around existing `bdfconv`)

### Phase 2 — Web Preview
- [ ] Browser-based XML → canvas renderer (JavaScript, not Wasm)
- [ ] Hot-reload on XML file change
- [ ] Font preview support
- [ ] Asset preview

### Phase 3 — Visual Editor
- [ ] Drag-and-drop widget placement
- [ ] Property panel for widget attributes
- [ ] Component palette (built-in + custom)
- [ ] Undo/redo
- [ ] Export to XML

### Phase 4 — Advanced Features
- [ ] Custom C-backed widgets (XML + C bridge)
- [ ] BDF font pixel editor
- [ ] Animation timeline (frame sequences)
- [ ] Multi-display support (e-paper, LCD, OLED)
- [ ] PlatformIO integration

## Verdict

> [!TIP]
> **This is a strong idea with a clear gap in the market.** No one has built a proper declarative-to-codegen pipeline for U8G2 monochrome displays. The existing tools (Lopaka, DisplayKit) are drawing tools, not frameworks. The existing frameworks (UiUiUi, PixelUI, MUI) are code-only with no declarative layer.
>
> The key risk is **scope creep** — trying to replicate LVGL Pro's full sophistication for a domain that doesn't need it. The monochrome constraint should be embraced as a simplifying force, not fought against.
>
> **Start with Phase 1 (CLI + XML schema + code generator).** Get something that compiles XML to working U8G2 code. Everything else builds on that foundation.
