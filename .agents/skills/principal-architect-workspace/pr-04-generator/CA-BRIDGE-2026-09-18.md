## 1. Bound positions inside a container — relative or absolute, and do children follow?

**Evidence (WO10 findings 2 and 3).** Authors write a child's literal coordinates relative to
its container; the resolver keeps them container-relative, and WO10's `emit/placement.ts`
translates them to device-absolute coordinates at build time, because the runtime draws in
absolute device pixels. Two cases the spec does not decide:

- **A bound child position** (`bind_x="offset"` on an element inside a container at x=40) is
  emitted as the raw subject value, i.e. absolute. An author who expects it relative to the
  container gets the element 40px to the left of where they meant.
- **A container whose own position is bound** moves at runtime, but its children's positions
  were fixed at build time, so they stay where they were. [D-20] already forbids *anchored*
  children of a geometry-bound container, but says nothing about children with literal
  positions.

**Options.**
- (a) Bound coordinates are container-relative, like literal ones: the generator emits
  `container_origin + subject` (the origin is a build-time literal, so this needs no runtime
  layout pass). A container whose position is bound may have no children with positions — a
  validator error — because they cannot follow without reflow.
- (b) Bound coordinates are device-absolute, documented as such; children of a position-bound
  container do not follow, documented as such, and the validator warns.

**Recommendation: (a).** It makes the same attribute mean the same thing whether it is written
literally or bound, which is what an author will assume, and it stays inside [D-20]'s "no
runtime layout" — the offset is a build-time constant. Forbidding positioned children of a
position-bound container is the honest consequence of having no reflow.

## 2. Generated identifiers can collide with C library names

**Evidence (WO10 finding 6).** §13.4 emits a screen-level object under its bare XML name
(`msg`, `title`) and reserves C++ keywords, but not C library names. An element named `clock`
becomes `static u8g2gl_clock clock;`, which conflicts with `clock()` from `<time.h>` whenever
that header is visible — and one of WO9's golden fixtures already contains exactly that.
Other likely names: `time`, `index`, `log`, `abs`, `rand`, `signal`.

**Options.**
- (a) Extend §13.4's reserved set with the C standard library's names. Whack-a-mole: the set
  depends on which headers a platform happens to include (Arduino pulls in a lot).
- (b) Prefix every emitted object identifier, e.g. `ui_obj_msg` or `ui_home_msg`, inside the
  generated namespace that `ui_` already reserves.

**Recommendation: (b).** It removes the whole class of collision rather than a list of known
cases, and it uses a prefix §13.4 already reserves for generated code. Cost: §13.4's table and
§13.12's worked example change, and the golden files churn once. Generated objects are
file-local and never referenced by application code ([D-20] §4), so no user code breaks.

## 3. Does a named style's font override an element's own `font=`?

**Evidence (WO10 finding 12).** §13.7's init order is construct → set properties → **apply
styles** → bind. Followed literally, an element that says `font="tall_12"` and also names a
style with `font="small_9"` ends up in `small_9`: the style, applied later, wins over the
element's own attribute.

**Recommendation: the element's own attribute wins.** It is the more specific statement of
intent, and it is how CSS and LVGL both resolve the same conflict. Either reorder §13.7 to apply
styles before properties, or keep the order and have style application skip properties the
element set explicitly. The first is simpler; I would take it.

## 6. Bounds for centre-positioned elements (WO8a finding 1)

**Evidence.** A `radius` is resolved and range-checked but never bounds-checked:
`<u8g2gl_circle x="10" y="10" radius="500">` on a 128-wide display validates. §7.2 deliberately
restricts anchors to rectangular elements and defers the semantics of centre-positioned ones
(circle, ellipse, pixel), so there is no rule to check against.

**Recommendation:** bounds-check a centre-positioned element by its bounding box —
`x − r … x + r`, `y − r … y + r` for a circle, `rx`/`ry` for an ellipse — against its container,
exactly as a rectangle is checked. Use the full box even when `segments` draws only a quadrant:
conservative, and consistent with how the clip window treats it. One sentence in §7.2.
